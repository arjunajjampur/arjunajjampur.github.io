Overview

An AI-powered metadata pipeline that autonomously generates and maintains a machine-readable component data dictionary for JPMorganChase's design systems — powering component selection, code generation, design-to-code workflows, and governance checks.

281 components covered — schema-validated, with props, variants, design tokens, ARIA accessibility data, composition rules, and usage guidance. In active use with 85+ designers across Investment Banking, Markets, Payments, and Security Services.

The structured 4-step walkthrough covers repo scaffold, data dictionary overview, and two key workflows: intent-based AI-augmented design and a Figma-to-code plugin. Under 2 minutes to go from zero to set up — with no terminal commands, no config files, and no design system knowledge required at the start.

The Problem

At enterprise scale, design system documentation is always incomplete — not because teams are lazy, but because keeping it current is expensive. A single component documented at real depth — props, tokens, ARIA metadata, composition rules, anti-patterns — takes hours. Multiply that by 281 components, then multiply it again every time something changes.

The documentation debt compounds silently until the system stops being trusted. I started asking a different question: what if an AI agent could maintain that documentation autonomously?

Architecture

Three principles govern the system:

Data-dictionary-first mandate — agents must read local JSON metadata before generating any UI code. No guessing props or tokens.

Layered system — Salt (core) → enterprise pattern layer → Global Banking overrides, with layer policies enforcing sizing rules, required states, anti-patterns, and token usage. GB override rules are highest priority and supersede all lower layers.

Anti-hallucination protocol — if a component, prop, or token isn't documented, the agent stops and flags it rather than guessing.

How It Was Built

Built solo, outside core responsibilities, across six phases.

Phase 01 Docs-only baseline Agent fetched data from Salt Storybook and the documentation site. Generated 61 schema-validated JSON files. 100% validation pass rate. Exposed every gap: zero design tokens, no anti-composition rules, incomplete props on 8 components. A clean baseline with honest failure modes.
Phase 02 GitHub enrichment Added TypeScript interfaces and CSS custom properties as a third data source. Tokens went from 0 to 161. Props coverage improved. Usage guidance went from 87% to 95%.
Phase 03 Schema v2 Evolved what the agent was asked to produce: broader token extraction, implementation notes, cross-referenced anti-composition rules. On the same 5-component sample, token extraction went from 14 to 68.
Phase 04 Enterprise pattern layer Extended generation to the internal enterprise pattern system using deterministic local enrichment — no API key required. 189 additional components generated and schema-validated.
Phase 05 Deep enrichment Real Storybook variants (400+), 600+ design tokens, pattern cross-references, and 438 enterprise-specific use cases. Metadata density up 47%.
Phase 06 Full enrichment ARIA APG patterns mapped to every component. Explicit sizing constraints. Best practices and common mistakes extracted from designer-authored Figma documentation. Layer policy files refactored to separate rigid guardrails from component-level detail.

Designer Workflow

Setup is a single npx command. Run it, answer a few prompts, and you're fully scaffolded in under 5 minutes — no terminal expertise required, no config files, no design system knowledge needed to get started.

From there, designers describe what they want to build in plain language. The agent reads the data dictionary, selects components per layer policy, generates code with all required states, applies design tokens, and marks output as VERIFIED / UNVERIFIED / PARTIAL. Quality gates — accessibility audit, token check, GB compliance review — run on demand.

Figma → Code

Vague prompts produce vague code. The highest-fidelity input path is a Figma plugin I built that reads a selected frame, extracts the full component JSON, and converts it into a structured prompt — with layer names, component hierarchy, and design intent intact.

That prompt, fed into VS Code with Claude and the data dictionary as context, produces output that is ~95% identical to the original Figma design — without the designer writing a single line of code.

Context is king in practice: the more precisely you describe the design intent going in, the less correction the agent needs coming out.

The Data Dictionary

Context is king.

Every decision in this system comes back to that principle. The data dictionary is not documentation — it is context, structured for a machine. The richer the context the agent has before it generates a single line of code, the closer the output is to what the designer intended.

That also means knowing what to leave out. I deliberately excluded internal animation timing, anatomy layer ordering, and spacing internals from the extraction — because an agent generating code doesn't need them. It needs best practices and common mistakes. Everything else is noise that degrades signal.

Layer policies are rigid guardrails that rarely change. Component JSONs are comprehensive and self-contained — everything an agent needs, nothing it doesn't.

Knowing what to leave out is harder than knowing what to include.

Fields That Matter

Most schema fields document what a component is. These three document what it does in context — the difference between plausible code and correct code.

composes_with — Components this one is designed to work alongside. Sourced from Storybook imports, TSX composition, and docs.

do_not_compose_with — Two valid components that are wrong together. Without this, the agent has no signal. Sourced from when_not_to_use cross-ref, GB overrides, and usage patterns.

domain_instances — Banking context mappings — how this component has been used across real GB screens. Empty at generation, filled over time. The system grows more accurate as it's used.

What This Proves

A design system can be made machine-readable at scale, maintained autonomously, and used to power AI-native workflows — component selection, vibe coding guardrails, design-to-code pipelines.

We're not far from a design system that doesn't wait for a designer to look something up. It already knows. It tells you before you ask.

That's not a better design system. That's a different kind of design system entirely.

What's Next

LOB-specific installers. Each line of business gets a tailored installer — built with designers from that team, not handed down to them. Having the same designers shape the tool they'll use means they have skin in the game, and the output reflects how their workflows actually run.

Adoption measurement. Instrumentation to track how the system is being used across teams — which skills get invoked, where designers drop off, and what the output quality looks like over time. Adoption without measurement is just hope.

Governance at scale. How do you keep an agentic system trustworthy as the underlying components change? How do you prevent an agent from confidently generating code against a component deprecated last Tuesday? That's the next hard problem — and the answer doesn't exist yet.
